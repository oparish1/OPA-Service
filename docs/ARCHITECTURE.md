# IDP Architecture

A snapshot of the codebase after the browser-only migration (issue #12) and the
standalone-frontend change (issue #30). See the root `README.md` for setup, the
public configuration file and the gateway configuration.

## Project overview

- **"Your Identity"** is a signed-in workspace where developers see their real
  identity, session and tokens, and call protected APIs (`/v1/me`,
  `/v1/projects`) with them.
- It is built as a **static browser app plus an external APISIX gateway**. The
  React SPA signs in directly with each identity provider, keeps tokens in
  memory only, and calls `/v1` through the gateway. The gateway validates every
  token and decides who may call what. There is no backend-for-frontend.
- **Providers:** Microsoft Entra ID, Okta and Google Workspace / Cloud Identity.
  The browser configuration file lists the enabled providers; a provider with no
  route in the external APISIX deployment is disabled and its route returns 404.
- **Version:** 0.1.0.

## Direction change (issue #12)

This issue is the maintainer's explicit decision to replace the earlier
backend-for-frontend direction. The following earlier decisions are
**superseded** and must not be read as current: O-05, O-08, O-09, O-10, O-15,
the server-side request runner and its safety rules, Invariant 5's server-side
session rules, and "Entra frontend and backend must remain untouched".

The BFF direction is recorded only for history in
`docs/auth/add-authentication-work-order.md` (now banner-marked superseded) and
in `.archon/design-decisions.md`. The Round 3/4/5 UI decisions remain binding
except where issue #12 explicitly reverses them.

## Direction change (issue #30)

Issue #30 makes this repository a standalone frontend. The in-repo
`authz-service/` policy copy and the local `gateway/` APISIX stack are removed;
the policy lives in `oparish1/authz-policy`, and APISIX runs outside this
repository. The browser evaluates capabilities only from the published WASM, and
`authz.mode` no longer exists: there is no gateway capability source. Real API
requests still go to the configured `gatewayUrl`, where APISIX enforces every
request.

## Architecture

- **Rule: each provider stays in its own folder.**
  - `frontend/src/core/` holds provider-neutral browser code. The Rego policy
    lives in `oparish1/authz-policy`.
  - `frontend/src/providers/{entra,okta,google}/` hold one provider each. Each
    provider's authorization policy is one file in `oparish1/authz-policy`; the
    published bundle exposes them at `authz/v1/gateway/{entra,okta,google}`.
  - `frontend/src/providers/index.ts` is the single frontend registry;
    `shared/providers.ts` defines `PROVIDER_IDS`; `shared/app-config.ts` defines
    the public-config schema.
  - `shared/provider-isolation.ts` fails the frontend suite if any other file
    names more than one provider id.
- **Browser auth core** (`frontend/src/core/`):
  - `providers/types.ts` is the one interface each provider folder implements:
    sign in, handle redirect, get access token, renew, sign out and session
    info, plus the parsed public-config slice.
  - `session/store.ts` is the only writer of tokens; it holds them in memory and
    owns the 30-minute idle and 8-hour absolute timers.
  - `api/runner.ts` is the direct gateway client: fixed gateway origin, an
    `AbortController` timeout, a response-size cap and the shared header
    allowlist.
  - `main.tsx` loads and validates `config.json`, installs the registry, handles
    the provider redirect callback and renders the app.
  - `authz/` loads the capability map once after sign-in and again after a
    renewal changes claims, caches one map and fails closed to a baseline floor.
    It always evaluates the policy that `bun run sync:policy` downloads from
    `oparish1/authz-policy`; there is no gateway capability source. UI
    authorization is advisory; APISIX enforces.
  - `generated.ts` (capability and reason ids) is generated by `bun run gen:authz`
    from the downloaded contract's `fixtures/capability-ids.json`. `AuthzClaims`
    is hand-written in `types.ts` because no published artifact carries the
    claim contract.
- **Authorization artifacts** (downloaded, gitignored):
  - `frontend/public/policy/` holds the pinned release's `policy.wasm`,
    `data.json` and `manifest.json`; the browser serves and evaluates them.
  - `frontend/policy/contract/` holds the matching `authz-contract` package:
    `authz/{catalogue,roles,role_map,routes}.json`, the persona and matrix
    fixtures, and the bundle-signing key. The generated types and the persona
    parity test read it.
  - The pin is `frontend/policy/VERSION`; `bun run sync:policy` verifies the
    release manifest and cross-checks the release catalogue against the
    contract's capability ids.
- **Gateway** is outside this repository. APISIX runs in declarative
  (standalone) mode with JSON access logs, no server banner and strict security
  headers. The deployment defines one v1 route per provider; its route files
  live outside this repository. Each route validates the bearer token with
  `openid-connect` and enforces the policy with `opa`; the provider wrappers in
  `oparish1/authz-policy` import the shared claim rules. The browser never reads
  capabilities from the gateway.
- **Tokens** are held in browser memory only. Per SD-3, a library without an
  in-memory option may use `sessionStorage` for that library only, with the risk
  recorded in the README and an A4 exception test. Tokens are never logged and
  never placed in a URL.
- **Accounts** are not linked by email; the gateway keys each request on the
  validated `(provider, issuer, subject)`.

## Tech stack

- **Language:** TypeScript (~5.6) everywhere. Bun is the runtime and package
  manager, with lockfiles committed.
- **Frontend:** React 18, Vite 5, lucide-react, `@azure/msal-browser`,
  `@okta/okta-auth-js`, the Google Identity Services script and
  `@open-policy-agent/opa-wasm`. Tests use Vitest 2, Testing Library and jsdom.
- **Gateway:** Apache APISIX (pinned 3.13.0) in declarative mode, deployed
  outside this repository. The policies are authored in `oparish1/authz-policy`
  and consumed there as a signed bundle.
- **Linting and CI:** ESLint 9 with typescript-eslint. GitHub Actions runs
  frontend checks and a gitleaks secret scan.
- **Tooling:**
  - `.archon/` holds Archon agent workflows for ship, audit, security gate,
    Figma and change readiness.
  - `.claude/skills/` holds deploy, CI and auth skills.

## Conventions

- Each module has a single owner, written down in doc comments like "the only
  file that names every provider" or "one owner".
- Closed enums and error codes such as `duplicate_provider_id:…` and
  `blocked_host`. It fails closed: unknown origins send nothing, an unset link
  is hidden, and a disabled provider route is absent.
- Tests sit next to each provider (`frontend/src/providers/*/__tests__`); the
  persona parity test compares the downloaded WASM with the downloaded matrix.
- Commit messages are short and imperative, describing the result.
- **Checks:** `bun run check` in `frontend/` runs lint, typecheck, build, test,
  `check:catch` and `check:authz`. `bun run build` and `bun run dev` run
  `sync:policy` first. The two provider-boundary scripts run from the repository
  root.

## Catalogue-driven authorization (issue #24)

The shared policy is data-driven and lives in `oparish1/authz-policy`: a neutral
Rego engine plus four static tables (`catalogue.json`, `roles.json`,
`role_map.json`, `routes.json`). That repo publishes the signed `authz-bundle`,
the `authz-contract` package and the WASM on each `v*` tag. This repo pins one
version in `frontend/policy/VERSION`; `bun run sync:policy` downloads the release
and the matching contract, verifies the manifest hashes and checks that the
release catalogue covers every contract capability. The browser evaluates the
WASM as advisory UI hints; APISIX remains the only enforcer.

`frontend/src/core/authz/generated.ts` is generated from the contract's
`fixtures/capability-ids.json` by `bun run gen:authz`, and `bun run check:authz`
fails CI when it is stale. The downloaded `fixtures/personas.json` and
`fixtures/matrix.snapshot.json` are the persona decision grid the parity test
asserts against. To add a capability, role or route: change and release in
`oparish1/authz-policy`, bump the pin here, re-sync and run the checks.
